# Spike B: run the Linux-built App.framework on a real iPhone

Status: done, 2026-10-16. **Result: PASS. Gate G0 ("counter app built on Windows runs on the iPhone") is met.**

## Question

Does the iOS release `App.framework` produced on Linux in spike A load and run on a real iPhone? That is, the Dart AOT snapshot from our Linux-built `gen_snapshot`, combined with Google's prebuilt `Flutter.framework`, with everything built, signed and installed from Windows through WSL2.

## Result

On an iPhone 15 (`iPhone15,4`) running iOS 27.0.1 (24A446):

- The app launched and showed the Flutter counter demo. Three taps on **+** showed **3** (observed on the device).
- The device log shows the engine starting: `CounterRunner(Flutter): [IMPORTANT:flutter/shell/platform/darwin/graphics/FlutterDarwinContextMetalImpeller.mm(45)] Using the Impeller rendering backend (Metal).`
- The device log has no snapshot, VM or crash errors.

## Pipeline

Scripts are in `spikes/b-device/`. Scratch work lives in WSL under `~/spikes/spike-b/`. No binaries are committed.

1. **Dart AOT (spike A1).** `make_app.sh` produces `App.framework`: `App`, `Info.plist` (`io.flutter.flutter.app`) and `flutter_assets/`.
2. **Stage.** `stage.sh` copies the runner package (`runner/`) and the prebuilt `Flutter.xcframework` to scratch.
3. **Build.** `build.sh` runs `xtool dev build`, which produces an unsigned `.app` that links only `Flutter.framework` through a SwiftPM binary target. It then copies `App.framework` to `Frameworks/App.framework`, where the engine looks for it (`FlutterNSBundleUtils.mm:13`, `FlutterDartProject.mm:126`).
4. **Device link (Windows).** Install Apple Devices (`winget install --id 9NP83LWLPZ9K --source msstore`). Run `start-apple-mobile-device.ps1` so Apple's device process listens on `127.0.0.1:27015`. Detach the iPhone from usbipd. Set `networkingMode=mirrored` in `.wslconfig`. Tap **Trust** on the iPhone once.
5. **Install.** `install.sh` runs `xtool install --usb` with `USBMUXD_SOCKET_ADDRESS=127.0.0.1:27015`. That provisions (registers the device, creates a development certificate, an App ID and a profile), signs inside-out, uploads and installs in **15 s**. stdin is closed, so xtool cannot revoke certificates. It didn't need to.
6. **Launch.** Tap the icon. xtool cannot launch on Linux (see finding 7). On the first launch, trust the developer profile and turn on Developer Mode.
7. **Logs.** `logs.sh` captures the device log with `idevicesyslog` over the same link.

Installed bundle:

```
CounterRunner.app/
  CounterRunner                  links @rpath/Flutter.framework/Flutter; rpath @executable_path/Frameworks
  Info.plist                     generated by xtool (CFBundleIdentifier rewritten by xtool at install)
  Frameworks/Flutter.framework/  prebuilt engine
  Frameworks/App.framework/      App (Linux-built), Info.plist (io.flutter.flutter.app), flutter_assets/
  embedded.mobileprovision, _CodeSignature/   added by xtool install
```

## Findings

1. **`App.framework` must be embedded, not linked.**
   - Dart's Mach-O writer emits neither `LC_DYLD_INFO_ONLY` nor `LC_DYLD_EXPORTS_TRIE`. That is also true of the official macOS output from the spike A oracle.
   - `ld64.lld` therefore refuses `-framework App` with "No LC_DYLD_INFO_ONLY or LC_DYLD_EXPORTS_TRIE found".
   - The engine finds the framework at runtime by bundle ID and path and `dlopen`s it, so linking isn't needed. winCode's bundler should link `Flutter` (and plugins) and copy `App.framework` in.
2. **usbipd cannot carry the install.**
   - usbmuxd in WSL logs `device unconfigured` when the device is attached. During the upload, the device itself reports `ERROR (on device): asyncReadComplete, message was too large (65536 bytes, max = 65535)`. USB/IP merges USB packets.
   - xtool then stalls at `[Connecting] 100%` (xtool-org/xtool#19 and #341; dorssel/usbipd-win#959).
   - Small requests (device info, provisioning) work over usbipd; the bulk upload doesn't.
3. **A working device link needs no admin rights or firewall rules.** It is Apple Devices on Windows, plus WSL mirrored networking, plus `USBMUXD_SOCKET_ADDRESS=127.0.0.1:27015`. It needed one "Trust This Computer" for the new path. This matches the plan's "Windows needs Apple's device driver".
4. **The Store version of Apple Devices has no Windows service.**
   - Its device stack is a startup task (`AppleMobileDeviceLauncher.exe` → `AppleMobileDeviceProcess.exe`), and it isn't running right after install.
   - Until then, the iPhone only exposes its photo/media interface (`MI_00`), and nothing listens on 27015.
   - `start-apple-mobile-device.ps1` starts the task inside the app's package context with `Invoke-CommandInDesktopPackage`. At the next sign-in it should start by itself; that was not verified.
5. **Password login needs xtool 1.22.2.**
   - xtool 1.21.0 got Apple's server-side `-80045` for every account.
   - A probe with a made-up account in a throwaway `HOME` returned `-80045` on 1.21.0 and `-20970` ("Your account information was entered incorrectly") on 1.22.2. On 1.22.2 Apple is checking credentials again.
   - Still open upstream: accounts with only SMS 2FA get HTTP 403 (xtool-org/xtool#345).
6. **First launch needs the user on the phone.**
   - xtool registers the App ID as `XTL-<account id>.dev.wincode.spike.counter`; it prefixes every App ID this way (`ProvisioningIdentifiers.swift`).
   - The first tap was refused with SpringBoard's "signature state: Needs Explicit User Trust" until the developer profile was trusted in Settings.
   - The log then shows SpringBoard restarting, which fits turning on Developer Mode.
7. **No automatic launch from Linux.**
   - xtool's `DDIMounter` stops with "DDIMounter does not yet work on Linux", so it cannot mount the developer disk image that launching through `debugserver` needs.
   - Release apps are launched by hand. Phase 3 (debugger and hot reload) needs its own path, as planned.
8. **The debug runner embeds build-machine paths.** Its `LC_RPATH`s include the scratch build directory and the swiftly toolchain path. They're harmless on the device, but they leak local paths; release builds must not ship them.
9. **Release Flutter logs almost nothing.** `Using the Impeller rendering backend (Metal).` is a reliable "engine started" marker.
