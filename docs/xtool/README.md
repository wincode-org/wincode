# xtool teardown

How xtool works, recovered from its source, as input for winCode's plan (`plan.md`).

- **Version:** xtool **1.22.2**, tag commit `65bf3cc` (2026-10-13). This is the version winCode runs.
- **Method:** xtool is MIT open source, so the analysis reads its code and traces each command through it. Three behaviours were also checked by running xtool; those checks are marked "tested".
- **Scope:** no Apple software was decompiled. The Apple ID password login uses Apple's private sign-in services, so it is described at architecture level only. winCode's supported path is the App Store Connect API key.

## Commands

| Command | What it does | Main code |
| --- | --- | --- |
| `setup` | `auth`, then makes sure the Darwin SDK exists and is current | `SetupCommand`, `SDKCommand` |
| `auth login` / `logout` / `status` | Login with an App Store Connect API key (`-m key`) or an Apple ID (`-m password`, `-u`, `-p`); `logout --reset-2fa` also forgets the pseudo-device | `AuthCommand`, `AuthToken` |
| `sdk install` / `update` / `remove` / `build` / `status` | Builds the Darwin Swift SDK from `Xcode.xip` or `Xcode.app`, or installs a prebuilt `darwin.xtoolsdk`; `--slim` uses less disk but can't self-update | `SDKCommand`, `SDKBuilder`, `DarwinSDK` |
| `new <name>` | SwiftPM template: `Package.swift` (iOS 17, macOS 14), `xtool.yml`, SwiftUI app and view; runs setup unless `--skip-setup` | `NewCommand` |
| `dev build` | Plans and builds the app, then packs an unsigned `.app` (or `--ipa`; `-s` signs) | `DevCommand`, `Planner`, `Packer` |
| `dev run` (default) | `dev build`, then the same install path as `install`. **It does not launch the app** | `DevRunCommand`, `IntegratedInstaller` |
| `dev generate-xcode-project`, `dev build-server` | Xcode project for macOS users; build server for editors | `XcodePacker`, `DevBSPCommand` |
| `ds teams` / `devices` / `certificates` / `identifiers` / `profiles` | Inspect and manage Developer Services objects | `DSCommands/` |
| `devices` | Lists usbmux devices (`--usb`, `--network`, `--all`) | `DevicesCommand`, `ConnectionManager` |
| `install <app or ipa>` | Provisions, signs and installs on a device | `InstallCommand`, `IntegratedInstaller` |
| `uninstall <bundle id>` | Removes the app through installation_proxy | `UninstallCommand` |
| `launch <bundle id> [args]` | Starts the app through the device's `debugserver` service (see "Launch") | `LaunchCommand` |

## Licences

- **xtool itself is MIT.** Copying its source is allowed; its copyright and licence notice must stay with it.
- **Most of its 51 pinned packages are permissive** (MIT, Apache-2.0, BSD-2-Clause), including `zsign`, `xtool-core` and `SwiftyMobileDevice`.
- **Copyleft parts:**
  - `xtool-org/xadi`: **LGPL-2.1**. Used by Apple ID password login.
  - `saagarjha/unxip`: **LGPL-3.0**. Extracts `Xcode.xip`.
  - The device libraries (libplist, libimobiledevice-glue, libusbmuxd, libtatsu, libimobiledevice): **LGPL-2.1**. They aren't vendored. `xtool-core` links them as system libraries; the Dockerfile builds them from source, and linuxdeploy bundles them as shared libraries into the AppImage.
- **What this means:** copying xtool's source copies no LGPL source. Shipping our *own* xtool binary would carry LGPL obligations: licence texts, a source offer, and relinkable shared libraries.

## Storage and secrets

- **Everything lives in `~/.config/xtool/`** (from `NSHomeDirectory()`, so `HOME` moves it). Key-value data is under `data/`, Anisette state under `Anisette/`. The live storage on every platform is plain files (`DirectoryStorage`); a Keychain backend exists but isn't the default.
- **The saved login (`XTLAuthToken`)** holds either the Apple ID session token or, in API-key mode, the **App Store Connect private key itself** (`AuthToken.swift`).
- **The signing certificate and its private key** (`SigningInfo`) are stored as a plist keyed by identity ID: the issuer ID for API-key logins, the team ID for Apple ID logins.
- **Tested:** on the spike machine these files are mode **644**, in a 755 directory, with umask 0022. Only the 750 home directory keeps other local accounts out.
- **The Darwin SDK** lives in `~/.swiftpm/swift-sdks/darwin.artifactbundle` (or `$XDG_CONFIG_HOME/swiftpm/...`).

## Darwin SDK (`sdk`, `SDKBuilder.swift`)

1. **Read the input.** It accepts `Xcode.xip`, `Xcode.app` or a prebuilt `darwin.xtoolsdk`. A `.xip` is recognised by its `xar!` magic bytes.
2. **Download two helpers from GitHub releases:**
   - the Linux toolset `xtool-org/darwin-tools-linux-llvm` v1.1.0: `ld64.lld`, `llvm-lib` (renamed from `libtool`) and `dsymutil`;
   - `OpenAppleMacrosServer` v1.3.0, used as the Swift macro plugin server.
   Downloads are checked **only for HTTP 200, with no checksum or signature verification.**
3. **Wrap the linker.** `ld64.lld` is replaced by a shell trampoline: lld can't do relocatable `-r` links, so those calls become a static archive built with `llvm-lib`.
4. **Extract Xcode.** unxip streams the xip. A path allowlist keeps:
   - the toolchain's `usr/lib/{swift,swift_static,clang}`;
   - for each of iPhoneOS, MacOSX and iPhoneSimulator: `Info.plist`, `Developer/SDKs`, `Developer/Library/{Frameworks,PrivateFrameworks}` and `Developer/usr/lib`.
   Prebuilt Swift modules are dropped. The "normal" flavor keeps a copy of `Xcode.app` and hard-links files so the SDK can update in place; "slim" copies files and can't update.
5. **Patch for Linux:**
   - Platform `Info.plist`: lld as the linker; `CODESIGN=true`, because signing happens after the build; Swift and clang resource directories.
   - Testing frameworks are symlinked into the SDKs.
   - Macro plugins are routed to OpenAppleMacros through stub `.so` files.
   - The host clang `include` directory is copied in.
6. **Write the SwiftPM bundle:**
   - `swift-sdk.json` with five triples (iOS device, iOS simulator arm64/x86_64, macOS arm64/x86_64);
   - `toolset.json` and `toolset-swb.json`;
   - `darwin-sdk-version.txt` (`epoch=3,darwinTools=1.1.0,oam=1.3.0`).
   A version mismatch triggers an update (normal flavor) or a reinstall.

## Build and packaging (`dev build`, `PackLib`)

1. **Plan** (`Planner`):
   - `swift package show-dependencies` and `describe` build the package graph.
   - The app is the single library product, or the one named in `xtool.yml`.
   - Each target's binary targets, resource bundles and dynamic-library dependencies become **resources** to embed.
   - `Info.plist` is generated (bundle ID from `bundleID` or `orgID.product`, `UILaunchScreen`, orientations, device family), then merged with `infoPath`.
   - App extensions come from `xtool.yml` `extensions`.
2. **Build** (`Packer`): it writes a hidden builder package, `xtool/.xtool-tmp`, with one executable target per product. Each target links the app library, with rpath `@executable_path/Frameworks`. It then runs `swift build` with `--swift-sdk` (SwiftPM) or `--triple` plus `--toolset` (SwiftBuild, the default on Swift 6.4).
3. **Pack:**
   - Copy the executable.
   - Copy dynamic binary-target frameworks to `Frameworks/<name>.framework`. Static archives are skipped.
   - Copy `lib<name>.dylib` products to `Frameworks/`.
   - Copy resource bundles, and `xtool.yml` `resources` to the app root.
   - Write `Info.plist`, adding `UIRequiredDeviceCapabilities`, `LSRequiresIPhoneOS` and `CFBundleSupportedPlatforms`.
   - The result is `xtool/<Product>.app`.
4. **Entitlements** from `xtool.yml` (`entitlementsPath`) are applied by ad-hoc signing the bundle. Provisioning later reads them back from the executable.

Frameworks that SwiftPM links are embedded automatically. Dart's `App.framework` can't be linked (it has no exports trie), so winCode embeds it after the build (spike B).

## Developer API and authentication

xtool has **one** generated client for Apple's developer API (`DeveloperAPI`, the App Store Connect API schema) and swaps the authentication middleware:

- **API key** (`DeveloperAPIASCAuthMiddleware`): the official App Store Connect API.
  - It sends a JWT signed with the user's `.p8` key: ES256, `kid` = key ID, `iss` = issuer ID, `aud` = `appstoreconnect-v1`.
  - The JWT lives 15 minutes and is renewed 2 minutes early.
  - There is no team object; the key's issuer is the identity.
- **Apple ID** (`DeveloperAPIXcodeAuthMiddleware`): the same requests are adapted to Apple's private Xcode developer-services gateway.
  - It uses a session from Apple's sign-in service: GrandSlam, password, then two-factor authentication.
  - It also needs per-machine provisioning data. The local `xadi` module produces it by loading a library from Apple's own Android app, which is downloaded from Apple at first use.
  - A remote provider for third-party servers exists in the code but isn't used by the Linux and macOS builds.
  - The selected team is the identity.
  - This path breaks when Apple changes its service. `-80045` was fixed in 1.22.2, and SMS-only two-factor authentication still fails (xtool-org/xtool#345).
- **Paging** follows the API's cursor links (`DeveloperAPIPages`).

## Provisioning (`DeveloperServicesProvisioningOperation`)

1. **Device:** registers the target device (name, iOS, UDID). "Already registered" (HTTP 409) counts as success.
2. **Certificate** (`DeveloperServicesFetchCertificateOperation`):
   - It reuses the stored development certificate if the team still lists its serial number and it hasn't expired.
   - Otherwise it generates an **RSA-2048** key pair and a CSR locally (`C=US, CN=xtool`, signed with SHA-1), and creates a new **development** certificate.
   - It **revokes** existing certificates only on a **free** team, after a "Continue?" prompt. Paid teams and API-key logins never revoke.
   - A fix for certificates whose serial starts with 0 landed after 1.22.2 (xtool-org/xtool#306).
3. **App ID** (`DeveloperServicesAddAppOperation`):
   - The app and its `PlugIns/` or `Extensions/*.appex` are provisioned, and their bundle IDs are rewritten to `XTL-<identity prefix>.<bundle id>`. Frameworks keep their own bundle IDs.
   - Entitlements are read from the executable. On free teams they're filtered to free capabilities.
   - Team and bundle IDs are rewritten, `get-task-allow` is forced on, and App Groups are created or assigned.
4. **Profile** (`DeveloperServicesFetchProfileOperation`): on **every install**, the App ID's existing profile is deleted and a new iOS development profile is created. It includes **every iOS device on the team** and the matching certificate.

## Signing

- **Plugin interface:** `Signer` is a C interface from `xtool-core`'s `SignerSupport`, and xtool's zsign fork (`Zupersign`) registers as its implementation.
- **One call signs the whole bundle**, nested frameworks included, with either the development identity or ad-hoc. The same plugin can read entitlements out of an executable (`analyze`).
- **Before signing** (`AutoSigner`): each provisioned bundle gets its rewritten `CFBundleIdentifier` and an `embedded.mobileprovision`.
- **To verify before relying on extensions:** `Signer.sign` keeps only the **app's** entry from the entitlement map (`SignerImpl.swift`).

## Device connection and install

- **Discovery** (`ConnectionManager`):
  - lists usbmux devices and follows add and remove events;
  - USB beats network for the same device;
  - libusbmuxd honours `USBMUXD_SOCKET_ADDRESS`, which is how winCode points it at Apple's Windows service (ADR-0005).
- **Connection** (`Connection`): pooled per device, with a lockdown session (handshake). While the phone shows "Trust this computer?" or is locked, the installer retries every 0.1 s and tells the user (`IntegratedInstaller.performWithRecovery`).
- **Install** (`AppInstaller`), used by both `install` and `dev run`:
  1. unpack into `Payload/`
  2. provision and sign in place
  3. zip
  4. upload over **AFC** to `/PublicStaging/XTool-App`, in 1 MB writes, after **reading the whole `.ipa` into memory**
  5. install through **installation_proxy**, with progress
  6. delete the staged file
- **Configure-device path:** an optional step enables Wi-Fi pairing and creates a second pairing record. `install` and `dev run` turn it off.
- **Unused code:** `ProfileManager` (misagent), `Debugger` and the iOS-only heartbeat are not on the install path.

## Launch

- **How it works:** `xtool launch` asks installation_proxy for the app's executable path and starts it through the device's **lockdown `debugserver` service** (`launch`, `qLaunchSuccess`, then detach).
- **Not tested:** on iOS 17 and later that service normally needs a mounted developer disk image.
- **Dead code:** xtool's `DDIMounter` (legacy, non-personalized images) has **no callers**, and on Linux it stops with "DDIMounter does not yet work on Linux".
- **Expectation:** `launch` fails on recent iOS from Linux. This needs one test with a connected iPhone (`plan.md`).

## Network and configuration

- **HTTP stack:** AsyncHTTPClient on Linux, URLSession on macOS. On Linux, Apple Root CA, G2 and G3 are added as extra trust roots (they aren't in the system store). The connect timeout is 60 s.
- **Environment variables:**

| Variable | Effect |
| --- | --- |
| `USBMUXD_SOCKET_ADDRESS` | (libusbmuxd) TCP usbmux address instead of `/var/run/usbmuxd` |
| `HOME`, `XDG_CONFIG_HOME` | Where the config and SDK live |
| `XTL_TMPDIR` / `TMPDIR`, `XDG_CACHE_HOME`, `XTL_DEBUG_TMP` | Temporary directories; keep them for debugging |
| `XTL_HTTP_PROXY` | `host:port` proxy for all HTTP |
| `XTL_DISABLE_TLS_VALIDATION=1` | Disables certificate checks (debugging only) |
| `XTL_DEV_LOG` | Regex; logs matching Developer API responses |
| `XTL_DEBUG_ERRORS` | Prints full error details |
| `SWIFTPM_CUSTOM_BIN_DIR` | Use a custom SwiftPM build |

## Running xtool without a terminal (tested)

Prompts read stdin through SwiftNIO. Without an interactive terminal, the first prompt fails at once, with exit code 1 and before any network call. It never loops:

| stdin / stdout | Result |
| --- | --- |
| `/dev/null` / regular file | `Error: Operation unsupported` |
| empty closed pipe / regular file | `Error: Operation unsupported` |
| empty closed pipe / pipe | `Error: I/O on closed channel` |

So a certificate-revocation question resolves to "no" and the install stops.

Prompts that a wrapper must answer through flags, or as lines on a stdin pipe:
- login mode
- key ID, issuer ID and key path
- Apple ID and password
- two-factor authentication code
- team choice
- device choice
- `Xcode.xip` path
- revocation confirmation
